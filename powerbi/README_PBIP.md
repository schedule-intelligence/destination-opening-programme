# Power BI project (PBIP)

`powerbi/DOP.pbip` is the Power BI project for the DOP schedule-intelligence model: a semantic model in TMDL
(`DOP.SemanticModel/definition/`, compatibility level 1702) and a report in the enhanced metadata format, PBIR
(`DOP.Report/definition/`).
It is generated by `python -m dop pbip` from the star-schema CSVs in `output/csv`, the measures in
`powerbi/measures.dax`, the theme `powerbi/dop_theme.json` and the model and page design in
[POWERBI.md](../POWERBI.md).

## Open it

1. Open `powerbi/DOP.pbip` in Power BI Desktop (October 2026 release, 2.159, or later). If Desktop refuses the
   file, go to File > Options and settings > Options > Preview features, tick **Power BI Project (.pbip) save
   option** and **Store reports using enhanced metadata format (PBIR)**, restart Desktop and open it again.
   The model is stored as TMDL (`DOP.SemanticModel/definition/`), the format Desktop writes for a project; it
   needs no option.
2. Home > **Refresh**. The project carries no data cache, so the tables are empty until the first refresh. The
   CSVs are read from the repository on GitHub (`output/csv` on `main`), so the project refreshes wherever it is
   cloned, with no path to set. The first refresh asks how to reach `raw.githubusercontent.com`: choose
   **Anonymous** (the files are public). To read CSVs that are not pushed yet, regenerate a local variant with
   `python -m dop pbip --csv-folder "V:\schedule-intelligence\output\csv"` and do not commit it.
3. File > Save as > Power BI file (`.pbix`) if you need a single file to share.

Desktop rewrites the project when it saves it: CRLF line endings, its own `$schema` versions, positions with
decimals and a `.pbi` folder. Commit that first save on its own. The repository's `.gitignore` keeps the per-user
files `.pbi/localSettings.json` and `.pbi/cache.abf` out of git.

| Trend lines | Section 0 of `measures.dax` defines two DAX functions, `DOP.AtUpdate` (a value at one update, the data-date slicer lifted) and `DOP.TrendSvg` (a KPI at every update up to the selected one, as an SVG picture), and each `[Trend - <KPI>]` measure is one `DOP.TrendSvg` call (POWERBI.md section 4, item 5). | `Update axis` | Hidden calculated table, one row per update (`SELECTCOLUMNS ( dim_snapshot, ... )`, POWERBI.md section 4, item 6), related to nothing: the x-axis of the table sparklines and the float bridge, which the data-date slicer therefore leaves whole. `update` ("Oct 2026") is sorted by `snapshot_id` |
| `Risk grid` | Hidden calculated table of the 25 cells of the risk map, probability x impact 1 to 5 each (`CROSSJOIN` of two `GENERATESERIES`, POWERBI.md section 4, item 7), related to nothing, so the map shows every cell |
| `_Measures` | All 119 measures from `measures.dax`, expressions unchanged (bar the function calls written out, see *Trend lines*), with display folders, descriptions and the format strings of POWERBI.md section 5 (dates `dd-mmm-yyyy`, day deltas `+0;-0;0`, ratios `0.000`, percentages `0.0%`, counts `0`). The four `... by update` measures (section 15) feed the table sparklines and the float bridge and take the format of the measure they read; they carry their pattern in full, because a table sparkline cannot follow its measure into a function (see below) |
| Extras from POWERBI.md | `fact_readiness[stage_order]` with `stage` sorted by it, `month_name` sorted by `month`, `label` sorted by `data_date`; hierarchies *Programme*, *P6 WBS* and *Calendar*; key and code columns not summarised; fact `snapshot_id` columns hidden |

Every page is 1280 x 720 (Fit to page), on an 8 px grid with 24 px margins and 16 px gutters.

- **Navigation rail** (left, 192 px): the programme name, a vertical **page navigator** of nine pages (the current page on a
  lighter tile with a teal accent bar; hidden and tooltip pages left out), a *Views* block with two bookmark
  buttons (*Decisions spotlight* and *Reset view*), and a *Source and controls* line bound to `[Provenance line]`
  (data date, baseline in force, controls passed, source file, DQ).
- **Title row**: the page name, then the page's action-title measure (`[Title - ...]`) as a wrapping headline,
  with the slicers at its right end: a single-select data-date slicer on `dim_snapshot[data_date]` (sorted newest
  first, opens on the latest update, synced across the pages) and, on pages 3, 6 and 9, the near-critical threshold
  slicer (opens on 10). Page 6 also has the *Offenders: check* dropdown there. The drill-through page has a Back

- **Content**: each page opens with one KPI strip (new card visual, no visual title: each tile has its label,
  and the page name and headline say what the strip is). Each tile shows a label, the value and one or two
  reference labels under it (the change since the previous update, the baseline variance, the share or the
  threshold); a tile in a strip with references always has one, so no tile shows an empty row. On pages 1, 2, 3
  and 6 each tile also has a trend line beside its value: the KPI at every update up to the selected one, a
  teal line over a light fill with the selected update marked, and a dashed red line at zero where the values
  cross it. The line is the tile's image (a `[Trend - ...]` measure, about a quarter of the tile, level with
  the value). It shares the width with the label, so those labels are short ("Late vs baseline", "Min float

  chart that proves the headline and the tables behind it. Charts carry a subtitle that says how to read them
  and reference lines where a level matters (zero float, BL0, DQ 85 and 70, the data date), with the line's
  label placed clear of the data. The hero line charts of pages 1 and 2 (Day 1 float, the gates) sit on a faint
  tinted plot area. They have no zoom slider: Desktop does not show one in a responsive visual this short.
- **Tables**: column widths come from the data. A code column (activity ids, file names: values without spaces,
  at most 22 characters) is as wide as its longest value; every column keeps room for the longest word of its
  header; dates stay whole. A table that shows a phrase column (names, asks, descriptions: values with spaces,
  over 30 characters) wraps it, so no name ends in "...". The scenario table is the exception: its names run to
  130 characters, so they are cut off and the cell's tooltip has the whole name. The shortfall, when the
  columns do not fit, comes from the columns with the most room above their minimum.
- **Sparklines**: the owner scorecard (page 6), the milestone table (page 2) and the risk register (page 5) have
  a sparkline column (Desktop's *Add a sparkline*): the row's DQ, variance vs BL1 or score at every update up to
  the selected one, a teal line with the last point marked in navy. Its x-axis is `'Update axis'[data_date]`,
  not `dim_snapshot[data_date]`, which the data-date slicer would cut to one point. The other values in those
  tables are sums, maxima or measures, so only the owner, milestone or risk defines a row; and each sparkline
  measure is blank unless the selected update has the row, so a table never lists a row the update does not
  have.

Only the visuals a bookmark names are captured, so the compare bookmarks leave the reader's data date as it is.
A data bookmark restores the whole data state of each visual it names, so it also carries that visual's own
filters (Open decisions, the 14-day look-ahead) and its sort: without them Desktop drops the filters and sorts
the table by its first column. A slicer that opens with nothing selected is cleared by removing its selection.

Each toggle is two pairs of buttons in the title row of the visual it switches: for each choice, a navy "on"
pill and a white "off" pill in the same place, and each bookmark shows one pill of each pair. The second chart
or table is a copy in the same box, hidden until its bookmark shows it. In Desktop editing, hold Ctrl to click a
button; in reading view and in the service a click is enough.

Checked in Desktop: BL0 then BL1 swaps the chart, the active pill, the selected tile and the table's variance
column together, and keeps a data date picked before (30-Jul-2026). Look-back and Risks swap their tables.
*Decisions spotlight* opens page 1 with the table in focus. *Reset* on page 3 brings the data date back to
29-Oct-2026 and clears the spotlight; on page 6 it clears a picked check (D02); afterwards both toggles are back
on look-ahead and decisions, the decisions table still lists only open decisions by due date, and the
look-ahead still lists only the next 14 days by start.

## Phone layout

Each visual that appears on the phone has a `mobile.json` (schema `visualContainerMobileState` 2.7.0) beside its
`visual.json`. Desktop's phone canvas is 324 units wide; the visuals stack in one column with 8-unit gaps:

1. the programme band (navy, as on the rail), the page name and the headline (9 pt on the phone: a visual title
   wraps to three lines at most);
2. the slicers: *Compare against* across the width, then the threshold and data-date slicers side by side;
3. the content in reading order (top to bottom, then left to right). KPI strips become a grid (arrangement
   *Grid*, as Desktop writes it). A strip whose references are caption | value pairs (pages 1, 2 and 6) gets
   one tile per row with 16 pt values and its trend lines: in a half-width tile the captions were cut ("vs
   BL..."). The other strips get two tiles per row with 14 pt values, so a date fits its tile, and no trend
   line, which would squeeze a half-width tile's label and value. Each toggle's buttons sit in a band of their
   own above the chart or table they switch, at their desktop distance from its right edge, so they do not
   cover its title. The risk map's five columns share the phone's width, the risks wrapped in their cells;
4. the *Source and controls* line on navy.

The page navigator and the rail buttons stay off the phone: the Power BI app lists the pages itself. The Gantt
page has no phone layout, because its bars need the width; phones show that page as it is, in landscape.

## Where it differs from the specification

- **Near-critical table name.** The what-if table is `'Near-critical threshold'` (column `Near-critical
  threshold`), not `NearCriticalDays`: `[Near-critical threshold (d)]` in `measures.dax` reads
  `'Near-critical threshold'[Near-critical threshold]`, and POWERBI.md section 4 uses that name.
- **Selected data date.** `measures.dax` has no `[Selected data date]` measure; `[Data date]` returns the
  selected data date (section 1 of the measures). The header shows the selection in the data-date slicer, so it
  has no separate date card.
- **Float on the activity page.** The float measures leave level-of-effort activities out, as the pipeline's
  summary does. The latest-update card and the float chart on page 8 therefore read `total_float_d` itself (on
  the latest update, and by data date), so a level-of-effort activity shows its own float there.
- **TMDL layout.** `DOP.SemanticModel/definition` holds `database.tmdl` (compatibility level 1702), `model.tmdl`
  (model properties and a `ref table` line per table), `relationships.tmdl`, `expressions.tmdl` (the `CsvFolder`
  parameter) and `tables/<table>.tmdl` (no `functions.tmdl`: the DAX functions are written out in the measures). `dop/tmdl.py` writes the folder from the generator's
  model and reads it back for the checks; properties come before nested objects in every file, which Desktop
  requires. There is no `model.bim`: a project holds one model format, and the generator removes a stale copy.
- **Integer keys.** `snapshot_id`, `first_snapshot_id`, `calendar_id`, `wbs_id`, `parent_wbs_id` and `date_key`
  are whole numbers, as in POWERBI.md section 2. The measures compare `snapshot_id` numerically
  (`dim_snapshot[snapshot_id] < _sid`). Text ids and codes are text.
- **Partition steps.** Besides `Csv.Document`, `Table.PromoteHeaders` and `Table.TransformColumnTypes`, each
  partition turns empty fields into nulls first, as POWERBI.md's `fnLoadCsv` does. Without it a text column keeps
  `""`, and measures that test `ISBLANK`, such as `[Look-back items]`, would count every row. Date columns whose
  values carry a time of day are typed as datetime and then as date. `fact_readiness` also gets `stage_order`
  (POWERBI.md section 2, step 4).
- **Gate forecast chart.** It plots each milestone's forecast as calendar days later than BL0, with the forecast
  date in the tooltip. BL0 is fixed per milestone, so each line moves exactly as the forecast date does, and the
  value axis stays numeric.
- **Offenders for the selected check.** No relationship links `fact_dcma_check` to `fact_dcma_offender`, so
  selecting a row in the DCMA table cannot filter the offenders. A dropdown on `fact_dcma_offender[check_id]`
  (*Offenders: check*) in the title row filters them instead, which leaves the offenders table the width for
  whole activity names.
- **Paired tables.** POWERBI.md section 6 puts the look-back beside the look-ahead (page 3) and the risk register
  beside the decision log (page 5). Side by side, each had about 500 px for six or seven columns, which cut off
  activity names, titles and asks. Here each pair shares one full-width box, with a toggle in its title row. On
  page 5 the same box also holds the 5 x 5 risk map of section 6, as the toggle's third choice.
- **Colour bands.** The matrix on page 1 uses the default threshold of 10 for the amber band. Page 1 has no
  threshold slicer, so the threshold there is always 10.
- **Extra visuals from POWERBI.md.** Page 1 also has the progress card, pages 3 to 7 have a card row, and page 2
  has the milestone finish profile.

## Regenerate and check

```powershell
.\.venv\Scripts\python.exe -m dop pbip                 # rewrites powerbi/DOP.pbip, DOP.SemanticModel, DOP.Report
.\.venv\Scripts\python.exe scripts\check_pbip.py        # offline checks; exit 0 = clean
.\.venv\Scripts\python.exe -m pytest -q tests\test_pbip.py
```

With Node.js, Microsoft's report CLIs add a second validation and drive the open Desktop through the Desktop
Bridge. The bridge needs Desktop June 2026 or later, with *Enable external tool access to Power BI Desktop through
secure local APIs* ticked under Options > Preview features.

```powershell
npm install -g @microsoft/powerbi-report-authoring-cli @microsoft/powerbi-desktop-bridge-cli
powerbi-report-author validate powerbi\DOP.Report        # Microsoft's PBIR validation
powerbi-desktop open powerbi\DOP.pbip                    # then refresh once
powerbi-desktop reload                                   # re-read the files after python -m dop pbip
powerbi-desktop screenshot-all --output-dir shots        # a PNG of every page
```

`powerbi-report-author validate` reports no errors and 14 warnings. Twelve say the 60 px title-row slicers are
shorter than the 76 px it recommends; in Desktop their headers show in full at 1280 x 720 (see the screenshots,
which were captured this way). Two say it does not know `ganttChart`, a Desktop preview visual.

`python -m dop pbip` is not part of `run --all`, so a project saved from Desktop is never overwritten by a
pipeline run. Run it only when you mean to replace the project, for example after the CSV columns or the
measures change. The output is deterministic: the same inputs give byte-identical files.

`scripts/check_pbip.py` validates each file against the schema named in its `$schema`, using copies of the
published schemas in `scripts/pbir_schemas` (MIT licence in that folder), and works with no network access. It
also checks that:

- every field in every visual exists in the model;
- every CSV column is typed;
- the relationships and types match POWERBI.md;
- every measure matches `measures.dax`;
- the theme validates against Microsoft's report theme schema (`scripts/theme_schema`) and is registered;
- every page background image is a registered image resource;
- the page folders match `pages.json`;
- no visual overlaps another or leaves the page (a visual hidden until a bookmark shows it, and a toggle button
  inside the visual it switches, may overlap);
- every content visual has a title (a KPI strip may hide its title if it keeps the text and alt text);
- every phone-layout box fits the 324-unit phone canvas;
- every bookmark is listed once in `bookmarks.json`, its pages and visuals exist, and every bookmark button
  applies an existing bookmark.

Desktop writes a `mobile.json` for a visual when its phone layout is edited, and its own bookmark files when one is
added. `python -m dop pbip` removes every file under `DOP.Report/definition` that it does not generate, so such
files go when the project is regenerated: make lasting changes in `dop/pbip.py`.

A file saved by a newer Desktop with an unpublished schema version is checked against the newest copied
version of the same major version, with a warning.

- **A theme colour in a button or a shape title goes white.** A `ThemeDataColor` fill on a bookmark button, the
